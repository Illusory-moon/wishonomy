# 架构：为什么这么写

> 这份文档记的是**决策与坑**，不是代码导读。改代码前先看这里。

## 1. 数据模型

四张表（SQLite，WAL）：

| 表 | 装什么 | 关键约束 |
|---|---|---|
| `account` | 钱包（含 bot 自己） | 主键 `(self_id, user_id)` —— **按用户全局，不按群隔离** |
| `ledger` | 一切数值变化 | `UNIQUE(kind, ref)` = 幂等；`group_id` 只是**来源记录** |
| `iou` | 未兑现的要求（欠条） | `UNIQUE(self_id, ref)`；status: open/delivered/defaulted/forgiven/refunded |
| `credit_event` | 信誉分变动 | 唯一依据，可回放 |

**为什么不按群隔离**：同一个人在哪个群都是同一个人，钱包跟着人走；
群号留在流水里，是为了回答"这笔愿力发生在哪个群"。记忆层按群分房是另一回事（那是语境，不是资产）。

## 2. 发行 vs 转账（**P1 写错过的第一个真 bug**）

「收愿力 / 分愿力」（`kind='mood'`）**不是转账** —— 愿力是被注视"带出来"的，
所以 `from_id` 写系统来源、对**任何人的余额都不做减法**。
会花光余额的动作只有一个：**送礼**（`kind='gift'`）。

> 第一版把 mood 写成了「从 bot 划给用户」⇒ 用户余额变成 **-7**，负余额。
> 自检 R05（余额永不为负）当场抓住 ✓ —— 这就是"每项断言都要真 `if`"的意义。

## 3. 事务与连接（**踩过的第二个坑**）

- 单 worker 线程池（`max_workers=1`）⇒ 账本操作天然串行，不需要跨账户锁。
  `ponytail:` 单 worker 是故意的（账本安全 > 并发）；真成瓶颈再换每账户锁。
- **写函数一律接收调用方给的连接**，函数内绝不再开新连接 —— 事务里开第二条连接会**互相等锁**（当场踩到 ✓）。
- 连接用 `isolation_level=None`（自动提交），事务边界由显式 `BEGIN IMMEDIATE` 划；
  否则 Python 的隐式事务会和显式 BEGIN 撞成
  `cannot start a transaction within a transaction`。
- 建表只在 `_connect()` 里做一次（幂等）—— 分成两处就会漏（第一版就是这么红的 ✓）。

## 4. 身份闸门（四条，fail-closed）

`enabled` / `enabled_self_ids` 白名单 / `sender == bot` 拒 / `cron_job` 轮拒。

⚠️ `@llm_tool` 是**全局注册**的：只要插件装了，**所有 bot** 都会看到这些工具。
所以闸门必须在**工具内部**再判一次（拿不到身份 ⇒ 一律不动账）✓

## 5. 缓存纪律（**账单红线**）

账本**绝不往每轮请求注入文本**。

- 工具说明（docstring）是常量，跟着工具定义走 = 稳定前缀 ✓
- 余额 / 流水 / 当日额度这类**每轮都不同**的内容一旦注入，**它后面的整段历史缓存全部作废** ⇒ 账单翻倍 ✗
- ⇒ 只做**按需查询**（工具），不做注入；**不许挂 `on_llm_request` 改 prompt**
- 自检 **R23** 把这条钉住（新增注入钩子会当场红）

## 6. 工具返回值的语义

有的框架把「工具返回 `None`」当成「工具已经把话直接发出去了」⇒ **直接结束本轮** ⇒ 群里静悄悄。
所以：

- 所有工具**一律返回非空字符串**（`tool_guard` 兜底：异常、None、非字符串全部转成人话）
- 自检 R07 / R21 守着这条

## 7. 认人（名字 → id）

- 只记「谁在这个会话里说过话」（`self_id|group_id|user_id → 昵称`），**不记聊天内容**
- 解析顺序：`你/你自己` → bot 自己；`我/我自己` → 当前说话人；昵称（**同名多人就不猜**）；纯数字 → 当作 id
- 缓存有 TTL（默认 7 天）与上限，超了淘汰最旧的

## 8. 分日

服务器时区是 UTC，账本一律按**北京时间**分日（`day_start`），
不然"每人每日上限"会在每天 08:00 忽然重置 ✗
