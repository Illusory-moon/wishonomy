# 架构：为什么这么写

> 这份文档记的是**决策与坑**，不是代码导读。改代码前先看这里。

## 1. 数据模型

四张表（SQLite，WAL）：

| 表 | 装什么 | 关键约束 |
|---|---|---|
| `account` | 钱包（含 bot 自己） | 主键 `(self_id, user_id)` —— **按用户全局，不按群隔离** |
| `ledger` | 一切数值变化 | `UNIQUE(kind, ref)` = 幂等；`group_id` 只是**来源记录** |
| `iou` | 未兑现的要求（欠条） | `UNIQUE(self_id, ref)`；status: open/delivered/defaulted/forgiven/refunded |
| `credit_event` | 信誉分变动 | 唯一依据，可回放 |

**为什么不按群隔离**：同一个人在哪个群都是同一个人，钱包跟着人走；
群号留在流水里，是为了回答"这笔愿力发生在哪个群"。记忆层按群分房是另一回事（那是语境，不是资产）。

## 2. 发行 vs 转账（**P1 写错过的第一个真 bug**）

「收愿力 / 分愿力」（`kind='mood'`）**不是转账** —— 愿力是被注视"带出来"的，
所以 `from_id` 写系统来源、对**任何人的余额都不做减法**。
会花光余额的动作只有一个：**送礼**（`kind='gift'`）。

> 第一版把 mood 写成了「从 bot 划给用户」⇒ 用户余额变成 **-7**，负余额。
> 自检 R05（余额永不为负）当场抓住 ✓ —— 这就是"每项断言都要真 `if`"的意义。

## 3. 事务与连接（**踩过的第二个坑**）

- 单 worker 线程池（`max_workers=1`）⇒ 愿力操作天然串行，不需要跨账户锁。
  `ponytail:` 单 worker 是故意的（中心安全 > 并发）；真成瓶颈再换每账户锁。
- **写函数一律接收调用方给的连接**，函数内绝不再开新连接 —— 事务里开第二条连接会**互相等锁**（当场踩到 ✓）。
- 连接用 `isolation_level=None`（自动提交），事务边界由显式 `BEGIN IMMEDIATE` 划；
  否则 Python 的隐式事务会和显式 BEGIN 撞成
  `cannot start a transaction within a transaction`。
- 建表只在 `_connect()` 里做一次（幂等）—— 分成两处就会漏（第一版就是这么红的 ✓）。

## 4. 身份闸门（四条，fail-closed）

`enabled` / `enabled_self_ids` 白名单 / `sender == bot` 拒 / `cron_job` 轮拒。

⚠️ `@llm_tool` 是**全局注册**的：只要插件装了，**所有 bot** 都会看到这些工具。
所以闸门必须在**工具内部**再判一次（拿不到身份 ⇒ 一律不动账）✓

## 5. 缓存纪律：**越不稳的放越后**

提示缓存是**前缀匹配** —— 中途改一个字节，它**后面**的所有内容都要按全价重算。
所以问题不是"能不能注入"，而是"**放哪**"：

| 内容 | 稳定性 | 位置 |
|---|---|---|
| 人格 / 规矩 | 一整天不变 | system_prompt 前部（框架管） |
| 工具说明（docstring） | **永远不变** | 工具定义里 = 稳定前缀 ✓ |
| `INJECT_TAIL`（那段说明） | **永远不变** | `system_prompt` **尾部** ✓（幂等补一句，不改它前面的字节） |
| 「他现在有多少愿力 / 信誉分」 | **每轮可能变** | `extra_user_content_parts` 的**最后一个 part** —— 框架把它接在**用户消息之后** ⇒ 变动只作废它自己 ✓ |

- **没有账户就一个字都不注入**（省 token 也省缓存）✓
- ❌ **绝不把变动的数字写进 `system_prompt`** —— 那会作废它后面的一切 ✗
- 兜底：老版本框架没有 `extra_user_content_parts` ⇒ 退回 `request.prompt` 尾部（位置差一点，但不丢数字）
- 开关：`inject_money`（默认开）；关掉 ⇒ 只靠 `wish_check` 按需查（更省 token，但那些轮她不知道对方有几个钱）
- 自检 **R23** 把这几条钉住：常量必须在末尾、数字必须在 parts 里、换人不许让系统提示变化、注入不许写库、
  开关与身份闸门都管得住注入 ✓

## 6. 工具返回值的语义

有的框架把「工具返回 `None`」当成「工具已经把话直接发出去了」⇒ **直接结束本轮** ⇒ 群里静悄悄。
所以：

- 所有工具**一律返回非空字符串**（`tool_guard` 兜底：异常、None、非字符串全部转成人话）
- 自检 R07 / R21 守着这条

## 7. 认人（名字 → id）

- 只记「谁在这个会话里说过话」（`self_id|group_id|user_id → 昵称`），**不记聊天内容**
- 解析顺序：`你/你自己` → bot 自己；`我/我自己` → 当前说话人；昵称（**同名多人就不猜**）；纯数字 → 当作 id
- 缓存有 TTL（默认 7 天）与上限，超了淘汰最旧的

## 8. 分日

服务器时区是 UTC，愿力中心一律按**北京时间**分日（`day_start`），
不然"每人每日上限"会在每天 08:00 忽然重置 ✗

## 9. 撤回的判据（P3 真踩过）

「**只在那笔钱对方一分没动时才撤得回来**」这条**不能**实现成"他之后有没有花过钱" ✗ ——
他花的可能是**自己的**钱（比如给自己攒的愿力送礼），那样会误判（R31 当场踩到 ✓）。

**唯一正确的硬判据**：`他的余额 >= 那笔金额` ✓
- 够 ⇒ 那笔钱还在（他花的准是别处的）⇒ 撤得回来，欠条转 `refunded`，写反向流水 ✓
- 不够 ⇒ 撤不回来（`code=spent`），而且**绝不扣成负数** ✓
- 「花了多少」只用来写回复文案，**不当门** ✓

另外一条顺序教训：`db_iou_grant` 里要**先判"欠条太多"再判余额** ——
顺序反了会给出误导的失败原因（R29 抓过 ✓）。

## 10. 她自己的钱只能靠送礼进来

`db_mood` 对 `who == self_id` **硬拒**（`code=self_mood`）；`db_iou_grant` 对 `who == self_id`
返回 `self_grant` ✓ ⇒ 她自己那份愿力**只有**「别人送礼」这一条进项，与设计稿 §1/§2 一致 ✓
（自检里给 bot 攒钱也因此只能走 `seed_bot()` = 让别人送礼 ✓）

## 12. 名字（别踩的撞名）

这套东西叫**愿力中心**，**不叫「账本」** —— 「账本」在本项目里已经指
bot 自己的笔记层（`save_note` 那套），两个东西撞名会把人绕晕 ✗

## 11. 发行侧的护栏（P2）

- **每人每日净增上限**：按**人**算（钱包跨群 ✓），不按群
- **全局日发行上限**：**只记 `logger.warning`、绝不拦她** ✓ ——
  依据设计稿 §2.1：「护栏拦的是"数量级"，不拦"她的意志"」；
  触发后 `wish_audit` 与日志都看得到 ⇒ 运营能自己调护栏 ✓
- **备份清单**：`data_paths()` 返回主库 + `-wal` + `-shm`；
  SQLite 的 WAL 边车若没一起备份，恢复时会丢最后几笔 ✗
- **配置热生效**：每次工具调用都现读配置（不缓存、不注册回调）⇒ 改完当轮就生效 ✓
